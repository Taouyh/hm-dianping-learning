## 3. 功能实现

### 3.1 店铺详情缓存

店铺详情使用以下 Key 结构：

```text
cache:shop:<id>
```

正常店铺数据以 JSON 字符串写入 Redis String，并设置缓存 TTL。查询流程是：

```text
先查 Redis
  ↓ 命中正常 JSON：反序列化为 Shop 并返回
  ↓ 命中空字符串：说明店铺不存在，直接返回空结果
  ↓ 未命中：查询 MySQL，成功后写入 Redis
```

### 3.2 缓存空对象解决缓存穿透

当数据库中不存在指定 ID 的店铺时，将空字符串写入 Redis，并设置较短 TTL：

```text
cache:shop:<id> -> ""
```

后续相同的非法 ID 请求会命中空值缓存，不再反复访问数据库。

### 3.3 互斥锁解决缓存击穿

使用：

```text
lock:shop:<id>
```

通过 Redis `setIfAbsent`（对应 `SET NX`，同时设置过期时间）保证同一店铺在缓存重建时尽量只有一个线程访问数据库。成功获取锁后再次检查缓存，避免其他线程已经完成重建却重复查询数据库。

### 3.4 逻辑过期与异步重建

逻辑过期方案不依赖 Redis Key 的物理过期时间，而是在 JSON 中保存：

```json
{
  "expireTime": "...",
  "data": { ... }
}
```

缓存未逻辑过期时直接返回；缓存逻辑过期时尝试抢锁，抢不到锁的请求直接返回旧数据；抢到锁后提交线程池异步重建缓存，当前请求仍返回旧数据。

## 5. 今天遇到的重难点

### 问题 1：List 缓存取出后应该转换为什么类型

- 问题：店铺类型列表写入 Redis 后，JSON 最外层出现 `[]`，误以为格式错误。
- 原因：`List<ShopType>` 序列化后本来就是 JSON 数组，单个 `ShopType` 才对应 `{}`。
- 解决过程：将 `JSONUtil.toBean(json, ShopType.class)` 改为理解 `JSONUtil.toList(json, ShopType.class)` 的对应关系。
- 最终结论：
  - `{}` 对应一个 Java 对象；
  - `[]` 对应一个 Java `List`。
- 我是否真正理解：🟡 理解后完成。

### 问题 2：缓存空对象中的 `null`、空字符串和正常 JSON

- 问题：不理解为什么先判断 `StrUtil.isNotBlank(value)`，后面还要判断 `value != null`。
- 原因：Redis 查询结果有三种状态：
  - `null`：Redis 没有这个 Key；
  - `""`：Redis 有 Key，但缓存结论是店铺不存在；
  - 正常 JSON：店铺存在。
- 解决过程：明确 `""` 是长度为 0 的空字符串，不是 `null`；`StrUtil.isNotBlank("")` 返回 `false`，但 `"" != null` 成立。
- 最终结论：第一个判断负责识别正常 JSON，第二个判断负责识别缓存的空对象。
- 我是否真正理解：🟡 理解后完成。

### 问题 3：为什么释放锁放在 `finally`

- 问题：最初认为数据库查询成功并写入 Redis 后就可以释放锁。
- 原因：数据库查询为空、Redis 写入异常或程序提前返回时，也必须释放已经获取的锁。
- 解决过程：理解 `finally` 会在正常返回和异常路径前执行；同时认识到不能在 `finally` 中写 `return`，否则会覆盖前面的返回值甚至吞掉异常。
- 最终结论：`finally` 用于统一清理资源，不能用于返回业务结果。
- 我是否真正理解：🟡 理解后完成。

### 问题 4：逻辑过期中的异步线程和锁释放责任

- 问题：获取锁后提交异步任务，为什么当前请求不等待新缓存，也为什么锁不能由请求线程立即释放。
- 原因：`submit()` 只代表任务提交成功，不代表数据库查询和 Redis 写入已经完成。若请求线程立即释放锁，其他请求可能重复提交重建任务。
- 解决过程：将释放锁放进异步任务的 `finally`；使用 `lockTransferred` 区分锁是由当前线程释放，还是已经转交给异步线程。
- 重点理解：
  - Double Check 发现缓存已被其他线程重建时，没有提交异步任务，当前线程必须释放锁；
  - 异步任务提交成功后，由异步线程在重建完成后释放锁；
  - `submit()` 失败时，不能假设异步线程会执行 `finally`，当前线程需要兜底释放。
- 我是否真正理解：🟡 理解后完成，仍需通过并发测试巩固。

### 问题 5：JSON 反序列化后的对象可能不是实体类，也可能为 null

- 问题：`RedisData.data` 声明为 `Object`，不能盲目写 `(Shop) redisData.getData()`。
- 原因：JSON 反序列化后，`data` 往往是 Hutool `JSONObject`，需要再次转换为 `Shop`；如果缓存结构中的 `data` 为 `null`，转换也可能失败或得到空对象。
- 解决过程：理解 `RedisData -> JSONObject -> Shop` 的转换链，并记录 `checkedResult`、`RedisData`、`expireTime`、`data` 均可能为空的边界情况。
- 我是否真正理解：🟡 已理解主要原理，边界处理尚未全部补齐。

### 问题 6：逻辑过期缓存与删除缓存策略的关系

- 问题：更新店铺时删除 `cache:shop:<id>` 后，逻辑过期查询方法可能读不到预热数据。
- 原因：逻辑过期方案通常依赖预先写入、只保存逻辑过期时间的缓存；更新方法当前采用的是删除缓存策略，两者混用时要考虑缓存缺失后的恢复路径。
- 最终结论：不同缓存方案不能只切换一个调用点，还要检查预热、缺失、更新和重建流程是否一致。
- 我是否真正理解：🟠 已发现并理解问题方向，尚未完成完整修正和验证。

## 6. Redis / 环境与工程排障经验

- 店铺缓存测试依赖后端、MySQL 和 Docker Redis 同时可用，不能只看接口代码。
- 共用 Redis 时需要注意逻辑库、Key 前缀和缓存删除范围，不能随意执行 `FLUSHALL`。
- 逻辑过期缓存没有依赖 Redis 的物理 TTL，测试前需要通过测试方法预热指定店铺数据。
- Maven 编译检查时使用了 JDK 17；本次环境检查受到 `target` 下资源/状态文件访问错误影响，因此没有把“编译命令异常”误判为业务代码编译成功。

## 7. 我的思考

- 缓存是数据库的加速副本，不是所有数据库更新都值得立即写入缓存；删除缓存可以等下一次真实访问时再回填。
- 逻辑过期牺牲短时间数据新鲜度，换取热点请求不被数据库重建阻塞。
- 对象整体读取适合 Redis String + JSON；需要频繁更新单个字段时，Redis Hash 更合适。
- 缓存方案的正确性不仅取决于主流程，还取决于并发、异常、空值和锁生命周期。
