# DAY-11 学习总结：用户签到与 Redis Bitmap

> 本文依据当前工作区的签到代码整理。签到实现主要是跟随教程完成并阅读理解，不等同于独立设计、编写或完成集成验证。

## 一、功能流程

```text
POST /user/sign 或 GET /user/sign/count
  -> UserController.sign/signCount()
  -> IUserService 对应方法
  -> UserServiceImpl 从 UserHolder 取当前用户
  -> StringRedisTemplate 读写当前年月的 Bitmap
  -> Result 返回操作结果或连续签到天数
```

`UserController` 负责 HTTP 路由并委托服务层；`IUserService` 声明用例；`UserServiceImpl` 负责取登录用户、生成 Redis key、执行位操作和封装结果。当前没有签到专用 Mapper 或数据库签到表访问，签到状态放在 Redis。

- `POST /user/sign`：无请求参数；取当前日期并将当天签到位设为 `1`，返回 `Result.ok()`。
- `GET /user/sign/count`：无请求参数；读取本月从 1 日到今天的位并统计从今天向前连续签到的天数，结果通过 `Result.ok(count)` 返回。
- 未登录时两个服务方法都会返回失败结果。重复签到会再次把同一位置为 `1`，不会累加出多次签到。

## 二、Key、日期与 Bitmap 位

常量 `RedisConstants.USER_SIGN_KEY` 是 `sign:`。`UserServiceImpl` 拼接方式为：

```text
sign:<userId>:<yyyyMM>
```

例如用户 `42` 在 2026 年 10 月使用 `sign:42:202610`。年月由 `LocalDateTime.now()` 和 `DateTimeFormatter.ofPattern(":yyyyMM")` 得到。当天日期 `dayOfMonth` 对应 Redis offset `dayOfMonth - 1`：每月 1 日是 offset 0，10 月 12 日是 offset 11。每个用户每个月一个 key，因此不同用户、不同月份的签到位互不混淆。

`sign()` 执行 `opsForValue().setBit(key, dayOfMonth - 1, true)`。`signCount()` 用 `BITFIELD GET unsigned(dayOfMonth) OFFSET 0` 一次读出从 offset 0 起的本月签到位，再按今天到月初的方向统计连续签到。`BITFIELD` 读取出的数值按位解释时，offset 0 位于读取整数的高位；今天对应读取结果的最低有效位，因此循环从最低位开始正好由今天向过去检查。

## 三、Redis 命令的用途与区别

- **SETBIT**：写指定 offset 的一位。项目签到接口用它标记当天为已签到；它只设置位，不保存签到次数或完整日期对象。
- **GETBIT**：读某个 offset 的单个位。适合查某一天是否签到；当前签到统计路径没有逐日调用 `GETBIT`。
- **BITCOUNT**：统计整个 key 或指定字节范围内值为 1 的位总数。它能算累计签到数，但不能直接得到“截至今天连续签到几天”；当前项目这段代码没有使用 `BITCOUNT`。
- **BITFIELD**：按指定类型和位范围批量读写字段。本项目用 `GET unsigned(dayOfMonth) OFFSET 0` 一次取回月初至今天的连续位段；不是用它写签到状态。

`BITFIELD` 返回 `List<Long>`，代码先检查 null/空列表，再取第一个 `Long num`。这里的 Long 是这些位按无符号二进制数解释后的十进制数值；Java 的 `&` 和移位会对该整数的二进制位运算，并非要先转成二进制字符串。当前读取宽度最多为 31 位，小于 Java `long` 的正数范围。

连续统计循环：

```java
if ((num & 1) == 0) break;
count++;
num >>>= 1;
```

`num & 1` 只检查最低有效位：0 表示对应日期未签到，连续段结束；1 表示已签到，计数加一。`num >>>= 1` 无符号右移一位，丢弃刚检查的最低位，让下一天来到最低位。由于位段以今天结束，第一位正是今天，然后依次向月初检查。代码先处理 `num == 0`，避免对全零情况进入无意义循环。

## 四、容易出错与边界

- 位 offset 从 **0** 起，不是从 1 起；日期 `d` 必须映射到 `d - 1`。
- `signCount` 取的是当月 1 日至今天，不会跨月统计连续签到。月初只读取当月位；跨月连续天数需另行设计，当前未实现。
- Bitmap 读取的位序要和 Redis offset、`BITFIELD` 整数位序一起理解；把 offset 0 错当最低位会反向统计。
- 日期和年月来自运行服务的 `LocalDateTime.now()`；部署时区若不符合业务时区，跨日边界可能与用户预期不同。当前代码未显式指定时区，也未对这一点做验证。
- 当天尚未签到时最低位为 0，连续数返回 0；本月 key 尚不存在时 Redis 对位段读取的实际响应需要以 Redis 行为/集成验证为准，当前代码对 null 或空列表返回 0，并对数值 0 返回 0。
- `SETBIT` 对重复请求是幂等的，但代码没有额外校验用户当天是否已签到，也没有签到时间、补签、过期策略或数据库持久化逻辑。
- 项目现有测试类没有签到专用测试；文档不据此声称 Redis 集成边界已验证。

## 六、复盘与面试回答思路

**1. 用户签到如何实现？** 按用户和年月构造 `sign:<userId>:<yyyyMM>`，用日期减一作为 Bitmap offset，通过 `SETBIT` 写 1；查询连续天数时 `BITFIELD` 取月初至今天的位段，再从今天对应的最低有效位开始计数。指出本项目状态存 Redis，没有签到数据库表或补签功能。

**2. 为什么用 Bitmap？** 每天只需一个二进制状态位，适合按用户、按月记录大量日期的简单存在状态，空间开销小；若需要记录签到时间、来源、补签审批等明细，单个位不能表达这些信息。

**3. `BITCOUNT` 和连续签到统计有什么区别？** `BITCOUNT` 得到范围内所有 1 的总数，不关心位之间是否连续；当前实现需要从今天开始遇到第一个 0 就停止，因此使用 `BITFIELD` 取数并在 Java 中逐位检查。

**4. `BITFIELD` 返回值与 Java 位运算是什么关系？** Redis 将指定位段解释为无符号整数并返回数值；Java 收到 `Long` 后直接按二进制位做 `& 1` 和无符号右移。回答要说明按 offset 0 起读取时整数位序与 offset 的映射，才能解释最低位为何代表今天。

**5. 日期、offset 和月份边界如何处理？** 每月独立 key，日期 d 映射到 d-1；统计只覆盖本月，因此不能计算跨月连续段。还需考虑应用时区与用户业务时区一致，以及月初读取宽度和当日位边界。

## 八、补充学习：UV 统计与 HyperLogLog

### 学习记录

- **UV（Unique Visitor）**：在指定统计范围内去重后的访客数量。统计范围（如按日、按活动）需要先定义；UV 关注“有多少个不同访客”，不同于 PV（访问次数）。
- **HyperLogLog**：Redis 提供的概率型基数估算结构，用较低且固定量级的内存估算大量输入中的不重复元素个数；结果存在误差，不适用于必须精确计数的业务。
- **实践边界**：本次跟随教程做过 HyperLogLog 测试，但没有修改黑马点评业务代码，也没有实现正式 UV 统计。不能把它描述为项目已有功能或精确 UV 结果。

### 与 Set、Bitmap 的选择对比

| 结构 | 适合的统计/查询 | 精确性 | 空间特点与限制 |
| --- | --- | --- | --- |
| Set | 精确去重；可检查某个 member 是否存在，也可读取成员 | 精确 | 每个不同 member 都需保存，基数很大时内存随成员数量增长 |
| HyperLogLog | 只关心不同元素的基数估算 | 近似，有误差 | 内存开销低；不保存可枚举的成员，不能据此查询具体访客 |
| Bitmap | 对可映射到整数 offset 的 ID/日期做存在标记，并统计置位数量 | 对已映射的位精确 | ID 范围稠密时紧凑；若 ID 空间很稀疏或最大 offset 很大，空间利用率可能差；不能枚举原始访客信息 |

选择时先看需求：需要精确去重且要找回成员，用 Set；只要大规模 UV 估算，用 HyperLogLog；对象能稳定映射为合理范围内的整数位置、且只需标记/计数状态时，再考虑 Bitmap。Set、HyperLogLog、Bitmap 并不能互相无条件替代。
